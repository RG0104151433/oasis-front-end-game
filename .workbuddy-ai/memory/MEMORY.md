# 项目长期记忆

## 用户偏好与项目约定

- 用户倾向于「先完善设计再高效推进项目」：不要在设计冻结前抢跑写故事数据、分支或引擎代码；先产出唯一、可裁定、可验收的设计定义包，再进入高效工程实现。
- 规划文档以设计先行、五轨并行设计、G0–G3 放行闸、变更受控、证据驱动为基线；设计冻结前只做资料盘点、决策、流程图、数据字典、验收用例等设计工作。
- 当前 Q 决策状态：Q3（以当前仓库 1.0 同构引擎为结构参照、冻结后重建最小 `story_config.js`）与 Q4（桌面浏览器、中英双语完整）已同意默认；Q6 用户倾向使用新场景重新绘制，范围待确认；Q1/Q2 受“后加第五/第六/第零线是否导致大量代码改动”影响暂缓裁定；Q5 需先解释“周目/多周目/错过窗口”后裁定。
- Q1 技术判断：现有 1.0 引擎的结局列表、requirements、事件、flags/clues、地图数据层已较数据驱动；只要在 G1 预留通用结局槽、状态命名空间、reviews/成就/音频/章节/预载的数据映射及 numeric/timer/slot 引擎能力，后加三组内容主要是数据、内容、美术、双语与验收增量，不必大量改引擎。若首发把四结局和章节链硬编码，则会形成 6–8 个文件的散点返工。
- Q1/Q2 新候选默认：设计全量覆盖六结局与第零线；首发实现可分期为四协议 + 一条 X 线；第五/第六/第零线作为第一内容包；美术新场景一次规划。是否把第零线纳入首发可玩版本取决于 Q6 新绘场景范围与内容/QA 承受量。
- Q5 术语：一周目 = 从新档到一次通关；二周目/多周目 = 通关后继承部分全局数据再从头玩（New Game+）；读档/重开当前关不算多周目。Q5 实际问的是第零线错过维护窗口后能否再入、是否写封条/失败态、通关后是否继承磁带、UI 是否提示。推荐首发不做多周目系统，选“同周目可再入、不写失败态、不提示、通关后不自动继承”。
- v1.2 复审结论：设计运行规划 S0–S4 阶段划分、G0–G3 放行闸、证据驱动与变更控制总体合理；主要执行风险是 G0 与 S1 的空窗、五轨并行协同成本、G1 缺少机读设计文件验收。v1.2 已新增第 18 节「规划合理性复审」与第 19 节「S1 落地执行细节」，允许 G0 通过前提前准备 A 轨草稿、B 轨六结局公式草稿、E 轨事件/状态字典初稿，但域冻结必须在 G0 通过后进行；G1 前需交付《事件/状态字典》与《六结局真值表》的 YAML/CSV 机读版本。
