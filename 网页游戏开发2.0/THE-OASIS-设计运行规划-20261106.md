## 0. 本版规划的调整点

上一版推进思路是“工程恢复与产品裁定并行，再汇入垂直切片”。本版按项目方偏好调整为：

> **先完成设计定义包并冻结，再一次性进入高效工程实现。**

具体变化：

| 项目 | 上一版 | 本版 |
|---|---|---|
| 首要动作 | 恢复可运行工程骨架 | 完成产品裁定与设计定义包 |
| 工程编码起点 | 设计裁定前即可补脚本 | 设计冻结前不启动故事/引擎编码 |
| 并行方式 | 工程轨 + 产品轨并行 | 五条设计轨并行，单一收口人 |
| 放行逻辑 | 工程恢复与裁定汇合后做切片 | 设计冻结 → 垂直切片 → 生产放行 |
| 高效手段 | 尽早跑通旧工程 | 先把返工源消灭，再用数据表批量落码 |
| 风险控制 | 用原型暴露问题 | 用设计评审与真值表提前消灭歧义 |

本文件取代上一版口头推进路线，成为下一阶段规划基线。

## 1. 当前起点（只列影响推进方式的事实）

1. 仓库 README 明确：`小学期网页开发/` 是 1.0 同构工程前身，`网页游戏开发2.0/` 是内容与规格；2.0 的 `oasis-game-draft` 工程本体不在本仓库。
2. `小学期网页开发/index.html` 引用但当前仓库缺少 `util.js`、`store.js`、`settings.js`、`shell.js`、`story_config.js`；`main.js` 在 `STORY_CONFIG` 缺失时直接退出。当前快照不是可运行基线。
3. 根基剧本自我定位为“已实现代码的剧本化转写”，是**叙事文本、世界观、硬约束与预算真源**，不是玩法系统、输入、存档、状态机或验收规则的 GDD 真源。
4. 叙事资产较厚：六幕主线、七条扩展线、四协议结局正文、reviews、voice bible、中英对白、资源预算基本成文；六份增量数据契约也已细化到节点、flag/clue、互斥与 reviews。
5. 但创作闭环仍缺：纯剧情版结局正文空白且有一处断句；六结局依赖的第五协议源文档不在当前仓库；第零线仍列三项待决策且被标为可选；M 线演出段数、四结局音频命名、若干“已定案”归属与裁定记录存在冲突或缺失。
6. R1/H2 的“已落码/通过”是历史文档声称，缺少当前代码版本、动态日志与可复现证据；不能作为继续批量落码的依据。
7. 已修订的 `百度搭子文档审阅-20261020.md` 应作为问题清单与证据边界参考，而不是设计真源。

结论：**现在最慢的做法是直接写分支代码；最快的做法是先把设计定义包冻结，再让代码从唯一数据表生成/录入。**

## 2. 规划目标与成功标准

### 2.1 目标

产出一个可评审、可冻结、可直接驱动编码与内容生产的 **DDP（Design Definition Package，设计定义包）**，并在冻结后以窄批次高效落码。

### 2.2 成功标准

- 同一需求只有一个当前权威定义；
- 每个结局、支线、跨线组合都有唯一合法路径；
- 首次进入、未完成、已完成、重入、回看、旧档、排除项、排除后补算均有明确语义；
- 文案、美术、音频、本地化、工程都能从同一份输入开工；
- 所有“已定案”都有确认人、时间、原话、影响文件与未决项；
- 设计冻结后，第一批内容不需要靠临场解释即可落码；
- 每个放行闸都有可复现证据，而不是“文档自称通过”。

### 2.3 非目标

本规划**不**包含以下动作：

- 不改写根基剧本正文；
- 不在设计冻结前重写 `story_config.js`；
- 不在设计冻结前修改 `engine/`、`store.js` 版本逻辑或四协议 requirements；
- 不迁移或删除现有文档；
- 不把历史 R1/H2 声明当成当前工程已实现；
- 不以“先做出来再说”替代产品裁定。

## 3. 核心原则

1. **设计先行**：设计冻结前不启动故事数据、分支、结局或引擎编码。
2. **决策先于文本**：未裁定的规则不靠补写对白、补写 reviews 来掩盖。
3. **单一真源**：DDP 是设计期唯一权威；根基剧本是内容真源；代码是运行真源；三者职责分离。
4. **并行设计、串行冻结**：五条设计轨可同时推进，但必须经统一评审口冻结。
5. **域冻结 + 全局冻结**：单个设计域达标即可域冻结，全部域达标后才允许进入编码。
6. **证据驱动**：每条“完成”都绑定版本、证据、评审人与验收结果。
7. **变更受控**：冻结后任何规则级变更必须走变更单并重跑受影响验收。
8. **范围切片**：首发范围与后续内容包分开，避免第零线/第五协议拖住主版本。

2. 指定四个执行角色：叙事负责人、系统/关卡负责人、工程接口负责人、验收负责人；允许一人多岗。
3. 确认本文件为推进基线。
4. 建立《决策记录》模板与《设计定义包》索引。
5. 冻结“当前资料快照”：记录本仓库路径、文档版本、已知问题清单，不改动文件。

### 5.2 必须先回答的产品问题

| 编号 | 待决项 | 当前建议 / 用户反馈 | 状态 | 影响 |

## 6. S1：五轨并行设计

五条设计轨可同时推进，但共用同一份《决策记录》和同一个术语表。每个工作包完成后立即评审并标记“域冻结”，不等其他轨全部完成。

| 轨 | 设计域 | 必答问题 | 主要交付物 | 域冻结条件 |
|---|---|---|---|---|
| A | 产品 / 范围 / 体验 | 首发玩什么、不玩什么；玩家每分钟在做什么；成功体验是什么 | 产品范围、体验目标、非目标、发布矩阵 | 与 Q1–Q6 一致；无“可选但影响主线”的模糊项 |
| B | 结局 / 规则 / 状态 | 六结局公式、排除项、兼得、显隐、seen/done、旧档补算 | 六结局真值表、状态机、requirements 红线、决策记录 | 所有结局组合可判定；C01/C02/C03/C06 关闭或明确移出首发 |
| C | 关卡 / 交互 / 时序 | 玩家从哪进、怎么走、何时可返回、四状态分别表现什么 | 地图路由、合法游玩时序图、交互与输入规则、回看/完成态定义 | 每条分支都有唯一路径；G01/G02/G03/G07 关闭或移出首发 |
| D | 内容 / 资源 / 双语 | 还缺哪些台本、分镜、音频、热区、key；纯剧情版如何修 | 穹顶终局台本、X4/第五协议处置、资源 manifest、双语与 voice bible 索引 | 文案/美术/音频/本地化可从唯一输入开工 |
| E | 验收 / 工程接口 | 设计如何变成可测数据；哪些能力引擎已有/待证 | 事件/状态字典、验收矩阵、before/after 规格、静态与动态用例 | 每个设计条目都有可验证断言；T01–T05 类证据缺口有补法 |

### 6.1 并行运行规则

- 每轨只维护一份当前稿，禁止复制“最新版-改2”文件；
- 术语、id、状态名统一从《事件/状态字典》引用；
- 跨轨冲突当天进入《决策记录》，不得在各自文档里私下改口径；
- 根基剧本只作为内容来源被引用，不在 DDP 内重写全文；
- 增量数据契约作为字段级输入，不自动升级为最终规则；
- 每个域冻结时记录版本、评审人、影响文件与未决项。

## 8. S3：工程准备与垂直切片

G1 通过后，工程侧才启动。此阶段只验证管线，不铺量实现全部支线。

### 8.1 工程准备

1. 补齐 `util.js`、`store.js`、`settings.js`、`shell.js` 与最小 `story_config.js`；
2. 固定 `index.html` 加载顺序、本地服务器、存档与双语基础链路；
3. 建立版本/哈希、before/after 快照、console 日志、输入存档与输出归档；
4. 把 DDP 的《事件/状态字典》转成静态校验规则；
5. 明确允许改动文件层，复核四协议 requirements 红线。

### 8.2 垂直切片范围

只做一条代表性路径，但必须完整：

- 进入 → 调查 → 一次演出 → 一个 clue → 一个互斥选择 → 写档 → 存读档 → 中英切换 → 一个结局 → 回看；
- 覆盖首次进入、未完成中断、完成后重入三种状态；
- 至少一条排除项不命中路径与一条命中路径；
- 绑定代码版本、输入档、命令、日志、预期/实际结果；
- 用第二条小内容验证同一管线可复现。

### 8.3 G2 放行条件

- 当前仓库可启动，核心循环经真实游玩验证；
- 静态校验与动态冒烟均通过；
- 第二块内容可按同一数据结构复现；
- 验收证据可重放；
- 无未绑定版本的“通过”声明。

每批固定动作：

```text
冻结输入 → 结构 diff → 静态校验 → 动态路径 → 存读档与双语 → 验收报告 → 版本归档
```

### 9.3 停工与返工触发条件

出现以下任一情况立即停止当前批次，退回 G1 或对应设计轨：

- 结局公式、排除项、兼得规则被修改；
- 新 flag/clue 进入四协议 requirements；
- 跨线顺序或回看语义重新定义；
- 动态验收失败且无法在当批内复现；
- 资源、双语 key 或热区坐标与 DDP 不一致；
- 完成声明无法绑定代码版本与证据。

## 15. 附录 A：Q1 后加三组内容的扩展成本评估

### 15.1 结论

**不会必然改动大量代码，但前提是设计冻结时就把扩展点预留好。** 当前 1.0 引擎已经是“数据驱动 + 少量硬编码注册”的结构：

- 若 DDP 把结局、状态、槽位、地图、资源、reviews、成就全部定义成数据表，后加第五协议、第六协议、第零线主要是**数据、内容、美术、双语和验收用例**的增量；
- 若首发把“四结局”“四个按钮”“固定章节链”“固定结局主题”写死，后加会变成 6–8 个文件里的散点修改，并触发全结局回归。不是重写整个引擎，但风险与返工量明显上升；
- 因此准确说法是：**代码可以不麻烦，内容/美术/验收一点都不会省。**

### 15.2 现有引擎已经数据驱动的部分

| 能力 | 证据 | 对后加内容的影响 |
|---|---|---|
| 结局列表动态读取 | `game-progress.js:62–85` 用 `Object.entries(this.cfg.endings)` 生成终局选择；`achievements.js:76–90` 也从 `STORY_CONFIG.endings` 生成回放列表 | 新增结局主要是 `cfg.endings` 数据 |
| 结局条件声明式求值 | `game-progress.js:47–60` 支持 `allOf / anyOf / noneOf / missingAnyOf` | 新隐藏结局可写 requirements 数据，不必新增判定函数 |
| 事件解释器 | `game-events.js:71–206` 用 `switch(ev.type)` 执行白名单事件；`changeMap / setFlag / ifClue / ifFlag / choice / finaleChoice` 等均在 | 新增节点/热区/对白是数据；新增事件类型才需要改引擎 |
| 存档状态 | `core.js:227–245、369–378` 的 `flags` 为 Set、`clues` 为数组、版本走 `Store.normalizeProgress` | 新 flag/clue id 可增量加入；但 `store.js` 当前缺失，旧档迁移规则必须在 DDP 写明 |
| 地图与关卡几何 | `game.js:299–309` 从 `cfg.maps[mapId]` 读取；`level-compose.js:89–91` 从 `ROUTE_DATA[mapId]` 读取 | 新地图可注册数据；但章节卡、预载链、氛围映射需同步 |
| 双语 | `i18n.js` 的 zh/en 字典与 `dialogueTree / dialogueTree_en` 成对机制 | 新文本按 key 成对增加即可 |

### 15.3 会造成散点修改的硬编码点

| 位置 | 当前硬编码 | 后加三线时的影响 |
|---|---|---|
| `game-progress.js:120–121` | 结局视觉主题只分 `inherit/dome` 与其他两类 | 第五/第六结局需要在数据中声明 theme，或改这里 |
| `audio.js:157–165` | `ending(kind)` 只特判 `inherit`，其余统一暖色和弦 | 新结局主题乐句需要数据化音频映射或小改 switch |
| `game-progress.js:128` | `dome` 专属追加 `dome_source_*` 文本 | 新隐藏结局若有专属结语，需要通用“ending append”机制 |
| `game.js:408–423` | `chapterInfo(mapId)` 手写地图章节标题 | 新场景需要补条目，或改为从 `cfg.maps` 读取 |
| `image-gate.js:18–24` | `_milestoneNext` 手写预载链 | 新地图需要补一行，或改为数据驱动 `next` |
| `game-progress.js:328–348` | `moodForMap` 手写地图氛围 | 新场景需要补 mood 或改为数据字段 |
| `achievements.js:71` | `REPLAY_CHAPTERS` 固定章节回放列表 | 新章节需要补列表或由 `cfg.maps` 生成 |
| `data/achievements.js:25–28` | 四个结局成就写死 | 新结局需要新 achievement id 与文案 |
| `game-events.js` switch | 未见 `numericAtLeast / numericTrack / timer / sixth slot` 等事件类型 | E 线数值、第零线倒计时、第六槽若按新能力实现，需要一次性加引擎能力，而不是后补 |

这些点单独看都不大，但分散在引擎、UI、音频、成就、预载、章节卡六类文件里；如果等到“后加三线”时才统一改，就必须重跑所有结局、存读档、双语、回看与资源加载验收。

### 15.4 让后加三组内容低成本的必备设计约束

G1 冻结前，DDP 必须写入以下约束：

1. 结局数量不写死；终局选择、结局回放、结局成就都从 `cfg.endings` 生成。
2. 信物槽/隐藏结局入口用列表数据驱动，不做“四个固定按钮”。
3. 所有结局条件用声明式 requirements；隐藏线只能新增自己的 conditions，不写进三协议 requirements。
4. 为 `fifth_* / sixth_* / zero_*` 预留状态命名空间；存档按可选字段处理，旧档缺省不报错。
5. reviews、结局主题、音频主题、章节卡、地图氛围、预载下一站、成就映射全部从数据表读取。
6. `numericAtLeast / numericTrack`、倒计时/暂停/后台、通用槽位显隐列为引擎能力矩阵；若需要，S3 垂直切片一次实现，不拖到后加内容时再改。
7. 资源 manifest 用 `contentPack` 标记首发/后续内容，避免后加时重新盘点全部图、热区、分镜、音频与双语 key。
8. 验收矩阵按“结局 × 排除项 × 访问顺序 × 存档中断”组合生成，新增内容只追加组合，不重写测试框架。

### 15.5 三种 Q1/Q2 路线对比

| 路线 | 代码改动 | 内容/美术/验收 | 风险 | 判断 |
|---|---|---|---|---|
| A：设计全量、实现分期、扩展点一次预留 | 后加三组内容以数据/资源/用例为主，引擎只在 S3 一次性补通用能力 | 若 Q6 新场景一次规划，可避免二次美术开工 | 低 | **推荐** |
| B：四协议首发，且完全不预留三线 | 后加时改结局 UI、存档归一化、reviews、成就、音频、章节卡、预载链，并全量回归 | 二次美术与二次内容生产 | 高 | 不推荐 |
| C：六结局与第零线一次首发 | 代码架构与 A 接近，因为设计全量；但首批内容/QA/资源最大 | 一次完成，前期压力最大 | 中 | 仅在 Q6 全量重绘且验收资源充足时选 |

### 15.6 对 Q1/Q2 的建议

- **Q1 建议改为**：`设计范围 = 六结局 + 第零线全量；首发实现 = 四协议 + 一条 X 线；第五协议、第六协议、第零线作为第一内容包；扩展点在 G1 一次预留。`
- **Q2 建议拆开**：
  - 第零线**进入首发设计与美术规划**：是；
  - 第零线**进入首发可玩版本**：待 Q6 范围与内容/QA 承受量决定。
- 若 Q6 选择“全部首发场景重绘”，美术一次开工，Q2 可偏向“是，首发可玩”；若 Q6 只是“新增/隐藏线场景重绘”，Q2 可保持“否，第一内容包”。
- 无论 Q1/Q2 最终选 A 还是 C，**六结局真值表和第零线状态机都必须在 G1 前完成**；否则“后加不麻烦”不成立。

## 16. 附录 B：Q5 周目与错过窗口说明

### 16.1 什么是“周目”

“周目”是游戏圈对一次完整通关流程的计数：

- **一周目**：从新存档开始，第一次玩到某个结局/通关；
- **二周目**：通关后不彻底清空所有数据，带着部分成就、图鉴、已看过的结局或特定继承项，再从头玩一遍；
- **多周目**：支持第三次、第四次……重复通关，并规定哪些状态继承、哪些重置；
- **读档 / 重开当前关 / 回看结局**不等于多周目，它们仍在同一周目内。

英文里常对应 `playthrough`、`New Game+ / NG+`。

### 16.2 Q5 实际在问什么

第零线方案里有一个“维护窗口”：

1. 图书馆可选调查点拿到 `zero_backup_tape`；
2. 终局过渡点出现第二选择「下行：离线湾」；
3. 进入第零章后有倒计时，耗尽会自动登出；
4. 玩家也可能不选、没拿磁带、或先走主线结局。

Q5 要决定的是：**玩家错过这次窗口后，还有没有机会再进第零线？这个“有没有机会”要不要写进存档？**

具体要回答四件事：

| 子问题 | 例子 |
|---|---|
| 同周目能否再入 | 没选「下行」后，回到 `finale_transition` 能不能再选一次？倒计时耗尽后能不能重进？ |
| 是否写“错过/失败/次数”状态 | 要不要写 `zero_missed`、`sixth_arc_sealed`，还是完全不记录？ |
| 通关后是否继承 | 一周目错过，二周目是否保留磁带/已看结局/封条？ |
| UI 是否提示 | 隐藏线完全不提示，还是给“维护窗口已关闭”之类反馈？ |

### 16.3 为什么这会影响代码

它不是文案偏好，而是存档与状态机设计：

- 决定 `flags / clues` 是否新增字段，以及 `Store.normalizeProgress` 是否要迁移旧档；
- 决定 `seen / done / sealed / eligible` 的生命周期；
- 决定结局回放、成就、图鉴是“本周目”还是“账号全局”；
- 决定第零线倒计时耗尽后清哪些瞬态、保留哪些持久状态；
- 决定旧档兼容：老存档没有新封条字段时，是直接判定可达，还是按排除项补算；
- 决定玩家公平感：隐藏线是“错过即错过”，还是“可以悄悄再试”。

当前资料对此有三种口径：方案 §4.2.3 写“错过即错过”，§7.3 又写“默认允许/建议可再入”，KM 契约 §8 写“可再入、不写失败态、多周目持带仍可进”。所以 Q5 必须在 G1 前由项目方选定一种。

### 16.4 可选方案

| 方案 | 玩家体验 | 存档/代码影响 | 适合情况 |
|---|---|---|---|
| A：同周目可再入，不写失败态，不提示 | 回到终局过渡点仍可再选；保持 EPHEMERAL 质感 | 不新增封条/次数字段；只需定义瞬态清理与重入条件 | **推荐；与 KM §8 最接近，首发最轻** |
| B：错过即永久错过，写封条 | 高压、不可逆；错过后本档永久关闭 | 新增 `sixth_arc_sealed` 写入点、旧档补算、UI/回放处理 | 想强调“窗口唯一”的叙事 |
| C：通关后多周目继承磁带重试 | 一周目错过，二周目还能补 | 需要真正的 New Game+：全局成就/图鉴与周目状态分离、继承白名单、存档版本升级 | 明确要做多周目系统 |
| D：完全不记录，每次新档重新发现 | 简单，但“通关后重玩”语义模糊 | 存档最轻；但回放/成就与周目边界要另定 | 只做单次体验的极简版 |

### 16.5 推荐

**首发不做多周目系统，但 G1 必须选定 A/B/C/D 之一。**  
建议选 **A：同周目可再入、不写失败态、不提供 UI 提示；通关后不自动继承磁带；多周目作为后续版本另立需求**。理由：改动最小、与已有 KM 裁定最接近、不会逼首发引入存档版本迁移；但需在《决策记录》里明确它覆盖方案 §7.3 的待决项，避免以后又按“默认允许下周目”实现出另一套语义。

## 17. 附录 C：Q6 新场景重绘影响

### 17.1 用户反馈

用户倾向：**使用新的场景重新绘制**。这替换 v1.0 的“复用现有场景与程序化绘制，不新增独立大图”默认。当前仍待确认的是范围。

### 17.2 需要确认的范围

| 选项 | 含义 | 对 Q1/Q2 的影响 |
|---|---|---|
| R1：全部首发场景重绘 | 主线、支线、终局、隐藏线场景统一新美术 | 美术一次开工；Q2 可偏向第零线首发可玩 |
| R2：仅新增/隐藏线场景重绘 | 主线沿用或轻修，新线使用全新场景 | 后加三线时美术增量可控；Q2 可保持第一内容包 |
| R3：核心主线重绘 + 其他复用 | 只重画玩家停留最久、最能体现新风格的主线场景 | 折中；需在 manifest 标出复用与重绘边界 |

### 17.3 对 DDP 的新增交付物

采用新场景重绘后，D 轨必须多交付：

- 场景美术 bible：风格、色板、透视、像素/分辨率、UI 叠层规则；
- 唯一场景 manifest：场景 id、背景图、尺寸/格式/命名、热区坐标、程序化兜底；
- 新场景与 `cfg.maps` / `ROUTE_DATA` / 章节卡 / 预载链 / 氛围音的映射表；
- 中英场景名、章节 ordinal、成就/回放条目；
- 资源失败兜底与加载预算；
- 验收用例：缺图、错图、热区错位、双语缺失、预载失败。

### 17.4 代码影响

新场景本身**不应导致引擎大改**：地图定义、背景图、热区、章节信息、预载链、氛围、成就与双语 key 都应当在 G1 被设计成数据表。当前需要同步的注册点主要是：

- `cfg.maps` 与 `ROUTE_DATA`；
- `image-gate.js` 的 `_milestoneNext`；
- `game.js` 的 `chapterInfo`；
- `game-progress.js` 的 `moodForMap`；
- `i18n.js` / `dialogueTree*`；
- `achievements.js` 的章节回放与结局成就；
- `audio.js` 的场景/结局主题映射。

若这些点在 S3 被改成数据驱动，后续增加新场景只是追加数据；若保持硬编码，每加一张新图都要回到上述文件补一行，并重新跑资源与章节验收。

### 17.5 与 Q1/Q2 的联动

- 选 R1 全量重绘：建议 Q1 走“设计全量 + 首发可玩范围尽早扩到六结局”，避免美术做完却把隐藏线内容雪藏；
- 选 R2/R3：Q1 可保持“设计全量、实现分期”，Q2 维持“第零线第一内容包”；
- 无论选哪种，Q6 都需要先确认“新绘场景是否进入首发验收范围”，否则 G1 的资源 manifest 无法冻结。

## 18. 规划合理性复审（v1.2）

### 18.1 复审结论

本规划 v1.1 的阶段划分、放行闸、证据驱动与变更控制总体合理，能够支撑“设计先行、冻结后高速落码”的目标。但存在 3 处执行风险，已在 v1.2 中通过第 19 节的落地细节与执行前提修正予以缓解：

1. **G0 与 S1 之间存在空窗**：v1.1 规定“G0 未过不启动 DDP 正式编写”，但 Q1/Q2/Q5/Q6 仍待裁定，团队容易在等待裁定期间停摆。
   - **修正**：第 19 节明确 G0 通过前可提前准备 A 轨产品范围草稿、B 轨六结局公式草稿、E 轨事件/状态字典初稿，但**不得域冻结**；G0 通过后直接进入 S1 正式编写与评审。

2. **五轨并行的协同成本被低估**：五条设计轨共用一份《决策记录》与术语表，若每个工作包都等全量评审会阻塞进度。
   - **修正**：第 19 节采用“小步评审 + 每日术语同步”机制：每个设计轨内部先做 2–3 个小评审，跨轨冲突当天进《决策记录》，域冻结只需一次全量评审。

3. **G1 检查表缺少“设计文件可机读”的验收项**：当前检查表偏人工审阅，未要求 DDP 能直接生成静态校验规则与验收用例。
   - **修正**：第 19 节要求 S1 结束时，E 轨必须交付《事件/状态字典》的 YAML/JSON 草案、《六结局真值表》的机读版本（CSV 或 YAML），并在 G1 评审时作为必查项。

### 18.2 未变更项

以下部分经复审后维持原样，无需调整：

- S0–S4 阶段路线与 G0–G3 放行闸的逻辑关系；
- 决策记录、状态词汇、变更分级与变更单字段；
- 与现有文档的冲突处理顺序；
- 附录 A/B/C 对 Q1/Q2/Q5/Q6 的技术分析与推荐。

### 19.3 五轨工作流（S1 内部节奏）

**每日节奏**（工作包驱动，非日历驱动）：

```text
09:00–09:30  术语同步（10 分钟）：检查《决策记录》新增条目、更新《事件/状态字典》
10:00–12:00  各轨工作包编写
14:00–15:00  跨轨小评审（每个工作包内 2–3 个小评审，避免全量阻塞）
16:00–16:30  冲突登记：当天发现的跨轨口径冲突写入《决策记录》
```

**工作包完成判定**：

1. 主责轨自检：交付物包含必答问题与交付物清单；
2. 会签轨会签：至少 2 条会签轨签字无异议；
3. 决策人确认：无“可选但影响主线”的模糊项；
4. 记录版本、评审人、影响文件与未决项。

满足 4 条后标记该工作包为“域冻结”，不等其他工作包。

### 19.4 五轨各自的关键任务与检查点

#### A 轨：产品 / 范围 / 体验

- [ ] 首发可玩范围：四协议 + 一条 X 线；第五/第六协议与第零线作为第一内容包
- [ ] 玩家每分钟体验目标：主线每幕的核心情感与操作目标
- [ ] 非目标：不做多周目系统、不做移动端适配、不做多人
- [ ] 发布矩阵：首发、第一内容包、后续版本的内容与资源边界
- [ ] 与 Q6 新绘范围联动：确定哪些场景进入首发美术批次

**检查点**：WP-A1 域冻结时，Q1/Q2/Q5/Q6 的裁定结论必须与产品范围一致；无“可选但影响主线”项。

- [ ] requirements 红线：第五/第六/零线只能新增 conditions，不改四协议 requirements
- [ ] 旧档补算：`zero_backup_tape`、`sixth_arc_sealed` 等字段缺失时的默认行为
- [ ] 第零线维护窗口：同周目重入、不写失败态、不提示、通关后不自动继承（Q5=A 推荐）
